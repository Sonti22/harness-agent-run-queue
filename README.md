# HARNESS — очередь запусков агента

Тестовое задание: Node.js 20+, TypeScript, `pg`, PostgreSQL. Отдельные сообщения
одного диалога выполняются по FIFO; разные диалоги могут выполняться параллельно.
В базе одновременно допускается один `running` на `dialog_id`.

## Запуск

Нужны Node.js 20+ и Docker Compose либо доступный PostgreSQL 16+.

```sh
npm ci
docker compose up -d --wait
```

Linux/macOS:

```sh
export DATABASE_URL='postgres://harness:harness_local_only@127.0.0.1:18765/harness_queue_test'
npm run db:migrate
npm test
```

PowerShell:

```powershell
$env:DATABASE_URL = 'postgres://harness:harness_local_only@127.0.0.1:18765/harness_queue_test'
npm run db:migrate
npm test
```

Пароль в Compose — публичный пароль отдельной локальной тестовой базы; порт
привязан к `127.0.0.1`. Для рабочего окружения задайте собственный DATABASE_URL.
Миграция транзакционная, повторный запуск ничего не меняет; изменение уже
применённого SQL обнаруживается по checksum. Зависимости фиксирует package-lock.json.

Тесты требуют настоящего PostgreSQL: они создают случайную изолированную схему и
удаляют только её. Нужна роль с правом `CREATE SCHEMA`. При отсутствии DATABASE_URL
тесты завершаются ошибкой, а не пропускаются. Рабочие таблицы тесты не очищают.

## API

```ts
import pg from 'pg';
import { RunQueue, LeaseLostError } from './src/queue.js';

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL });
const queue = new RunQueue(pool, { leaseMs: 30_000 });

await queue.enqueue('dialog-42', 'message-1', { text: 'Привет' });
const run = await queue.claim('worker-1');
if (run) {
  const ownership = { workerId: run.worker_id, leaseToken: run.lease_token };
  try {
    // Выполнить короткую работу; для длительной работы регулярно вызывать renew().
    await queue.renew(run.id, ownership);
    await queue.complete(run.id, ownership, { answer: 'Готово' });
  } catch (error) {
    if (!(error instanceof LeaseLostError)) {
      // При утрате lease fail() тоже отклонит прежнего владельца.
      await queue.fail(run.id, String(error), ownership);
    }
  }
}
await pool.end();
```

| Метод | Поведение |
| --- | --- |
| `enqueue(dialogId, idempotencyKey, payload)` | Возвращает новый или существующий запуск; другой payload при том же ключе — `IdempotencyConflictError`. |
| `claim(workerId)` | Возвращает запуск с токеном владения или `null`, если сейчас нет доступной работы. Сначала восстанавливает просроченные lease. |
| `complete(runId, ownership, result?)` | Записывает результат и `completed`, только если попытка ещё владеет действующим lease. |
| `fail(runId, error, ownership)` | После попыток 1–2 возвращает запуск в `queued`; после попытки 3 ставит `failed`. |
| `renew(runId, ownership)` | Продлевает действующий lease; истёкший lease воскресить нельзя. |
| `recoverExpired(limit = 100)` | Возвращает число восстановленных запусков. После третьей попытки просроченный запуск становится `failed`. |

**Дополнение к сигнатурам ТЗ:** `complete()` и `fail()` требуют `ownership`.
По одному `runId` невозможно отличить зависшую прежнюю попытку от текущей.
Токен — случайный UUID каждой попытки, а не монотонный fencing counter для
внешних хранилищ. Он защищает те операции очереди, которые его проверяют.

## Ключевой механизм

1. `enqueue()` блокирует строку `dialogs`. Порядковый номер выделяется внутри этой
   транзакции. Одновременные сообщения получают порядок по сериализации в БД,
   а не по времени на клиентском устройстве. Повторный enqueue не расходует номер.
2. `claim()` в короткой транзакции `READ COMMITTED` выбирает диалог через
   `FOR UPDATE OF d SKIP LOCKED`. **Следующим SQL-запросом**, после захвата строки,
   перечитывает первый незавершённый запуск. Если он `running`, выдачи нет.
3. Первый `queued` становится `running`, счётчик `attempts` растёт, выдаются
   `worker_id`, `lease_token` и `lease_until`. Частичный уникальный индекс —
   дополнительная защита от второго `running`, в том числе при ошибке кода.
4. Все изменения используют порядок блокировок `dialog -> run`. Завершение,
   ошибка и heartbeat проверяют токен, worker_id и срок lease **после ожидания
   блокировок**. Используется время PostgreSQL `clock_timestamp()`.
5. Просроченный запуск возвращается в очередь либо становится `failed`, если уже
   было три попытки. Второе сообщение не обгоняет повторные попытки первого.
   После окончательного отказа следующее сообщение разрешено выполнять;
   сведения об отказе остаются в `runs.error` и `dialogs.last_error`.

Почему два SQL-запроса в claim: снимок состояния при выборе кандидата может быть
старше commit другого воркера. Новый запрос на READ COMMITTED получает свежий
снимок. В тесте этот промежуток воспроизводится детерминированной PostgreSQL
advisory-barrier, без расчёта на случайный тайминг.

Документация: [PostgreSQL READ COMMITTED](https://www.postgresql.org/docs/16/transaction-iso.html),
[SELECT / SKIP LOCKED](https://www.postgresql.org/docs/16/sql-select.html),
[транзакции node-postgres](https://node-postgres.com/features/transactions).

## Отказы и границы гарантий

- Падение до commit `claim()` не расходует попытку. Падение после commit расходует:
  истекший lease позволяет выдать запуск повторно. Максимум — три выдачи всего.
- Воркеры должны вызывать `renew()` для длительной работы, например каждые 10 с
  при lease 30 с. При утрате lease нужно отменять работу, насколько это возможно.
  Библиотека не содержит агента, heartbeat-таймера или отправки писем.
- Lease не останавливает физически прежний процесс. Гарантия — один актуальный
  владелец в БД и отклонение прежнего результата, а не отсутствие любого
  физического перекрытия вычислений после истечения lease.
- Внешние действия требуют собственной идемпотентности, например стабильного
  ключа `run.id + ':send-email:1'`, одинакового между попытками. Эта библиотека
  не реализует адаптеры внешних систем и не гарантирует exactly-once.
- Если ответ от COMMIT потерян, исход операции может быть неизвестен. Повторять
  enqueue можно с тем же ключом; перед повтором внешних действий нужно сверить
  результат с внешней системой. Повторный complete после успешного complete
  выдаёт LeaseLostError: вызывающий код должен сверить сохранённое состояние.
- Повторы немедленные, без backoff. Нет гарантии глобального FIFO / fairness
  между диалогами. Это небольшой модуль задания, не промышленный диспетчер.
- `claim()` имеет ограниченный поиск (до 64 кандидатов), recovery — пакетный.
  `null` означает «сейчас нечего забрать», а не «очередь навсегда пуста».
  Вызывающий воркер повторяет опрос с паузой; recovery можно запускать отдельно.
- Payload должен быть обычным JSON. Сравнение при дедупликации семантическое,
  через JSONB: порядок ключей объекта не влияет. До БД отвергаются undefined,
  NaN/Infinity, циклы и объекты с нестандартным прототипом.

## Проверки

21 интеграционный тест на настоящем PostgreSQL:

- 24 конкурентных enqueue с одним ключом; конфликт payload; scope ключа.
- 3 конкурентных воркера, 72 задачи, 6 диалогов: отсутствие пересечения в одном
  диалоге, наблюдаемое пересечение между разными, FIFO и отсутствие дублей.
- Три попытки, окончательный failed, сохранение ошибки и освобождение диалога.
- Падение воркера через истечение lease; новый токен; конкурентное восстановление.
- Отказ устаревшему владельцу на complete/fail/renew, включая повтор worker_id.
- Гонка complete/fail, heartbeat и уникальный индекс при обходе модуля.
- Две детерминированные гонки: старый снимок кандидата и lease, истёкший во время
  ожидания блокировки. Recovery пропускает заблокированные диалоги.

GitHub Actions выполняет установку из lockfile, повторную миграцию и весь набор
на Node.js 20, 22 и 24 с PostgreSQL 16.4. Результат конкретного запуска доступен
во вкладке Actions; успешные тесты не означают проверку в production.

## Использование ИИ: реализация и проверки

При выполнении задания использовался Codex. Ниже перечислен фактический вклад
ИИ; самостоятельные действия кандидата ему не приписываются.

1. Сгенерировал SQL-схему `dialogs` и `runs`, ограничения состояния, уникальность
   ключа сообщения и частичный уникальный индекс одного `running` на диалог.
2. Реализовал `enqueue()` с дедупликацией по `(dialog_id, idempotency_key)` и
   проверкой совпадения payload через JSONB; другой payload вызывает конфликт.
3. Реализовал выделение номера сообщения под блокировкой диалога и FIFO внутри
   диалога, включая сохранение порядка при повторных попытках.
4. Реализовал `claim()` на `READ COMMITTED`: короткая блокировка строки диалога
   через `SKIP LOCKED`, отдельное перечитывание очереди и атомарная выдача задачи.
5. Добавил `worker_id`, `lease_until` и случайный токен каждой попытки; расширил
   `complete()` и `fail()` данными владения для отклонения прежнего владельца.
6. Реализовал `renew()` и пакетное восстановление истёкших lease. Попытки считаются
   при выдаче; после третьей неудачной попытки запуск становится `failed`.
7. Написал транзакционный скрипт миграции с повторным применением без изменений
   и проверкой checksum. При ревью нормализовал переводы строк для Windows/Linux.
8. Написал 21 интеграционный тест на настоящем PostgreSQL. Среди сценариев:
   конкурентная выдача, FIFO, повторы, истечение lease и старый токен владельца.
9. Включил в тесты обработку 72 задач тремя конкурентными async-воркерами и
   детерминированные проверки старого снимка кандидата и lease после ожидания замка.
10. При ревью доработал освобождение клиента пула: если rollback не удаётся,
    повреждённое соединение не возвращается в пул для повторного использования.
11. Подготовил Docker Compose, строгую TypeScript-сборку, lockfile зависимостей,
    инструкцию запуска и GitHub Actions на Node.js 20, 22 и 24 с PostgreSQL 16.4.
12. Выполнил два прохода проверки: на Windows/Node.js 24 и из чистой копии GitHub
    на Linux/Node.js 20. В каждом прошли все 21 тест; проверил успешный CI.
13. Дополнительно отдельным диагностическим скриптом проверил три ОС-процесса
    на 120 задачах, FIFO и параллельную работу разных диалогов. Эта проверка
    не входит в 21 тест репозитория и не выполняется текущим CI.
14. Отдельно принудительно завершил процесс после выдачи задачи, дождался
    реального истечения lease и проверил перевыдачу с новым токеном и отклонение
    старого владельца. Этот сценарий также проверялся вне текущего CI.
15. На PostgreSQL проверил замечания о `null`: JSON `null` успешно сохраняется
    при `NOT NULL`, повторный `enqueue()` возвращает тот же запуск. Предполагаемые
    ошибки смешения JSON `null` и SQL `NULL` в текущем коде не подтвердились.
16. При последующем ревью воспроизвёл два крайних случая в `encodeJson()`:
    getter может менять значение между проверкой и сериализацией, а собственный
    `toJSON()` массива — заменять проверенное содержимое. **Эти дефекты пока
    не исправлены в текущей реализации.**

ИИ также описал границы решения: lease не останавливает прежний процесс
физически; внешние действия требуют собственной идемпотентности; exactly-once
для всей цепочки не заявляется. В библиотеке нет самого LLM-агента,
автоматического heartbeat, backoff и гарантии fairness между диалогами.

Личные проверки и исправления кандидата следует описать отдельно после их
фактического выполнения. Например, самостоятельное исправление валидации
getter/setter и `toJSON()` должно подтверждаться изменением кода и тестами.
